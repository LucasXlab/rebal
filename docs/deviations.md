# 与 SPEC 的偏差记录

写代码时遇到的每个歧义都按"最简可行 + 记一条"处理。这里按发现顺序编号；
改过 SPEC 的地方也列出来（写代码时发现规格本身不自洽，就回头改规格而不是偷偷实现）。

## D1 错误块首行附上机器码

- SPEC §4.8 定义的错误块是三行：`rebal: error: 一句话` / 具体问题 / 怎么办。
- 实现里第一行是 `rebal: error: 一句话 [机器码]`。
- 理由：用户提 issue 时贴第一行就能定位；机器码本来就只出现在 `--json` 里，
  加在人类可读输出里不增加新概念。测试（T16/T21 等）也按"错误里能搜到机器码"来断言。

## D2 错误日志用 JSONL，不是自由文本

- SPEC §4.1 只规定"保留最近 20 条、单条 ≤ 8 KB"，没规定格式。
- 实现是一行一条 JSON（`{time, code, exitCode, message, details, stack?}`）：截断、裁剪、
  测试断言都简单，人也能直接读。时间戳用真实时间而不是注入的时钟——时钟坏了也必须能写日志。

## D3 `skipped` 的顺序改成按 `[targets]` 的顺序

- SPEC §3.6 的示例里 `skipped` 是 `bond` 在前。
- 实现按 `[targets]` 里类别的声明顺序输出（`us_equity`、`cn_equity`、`bond`），
  同类别再按原因排。理由：这个顺序对用户稳定可预期，也便于 diff 两次输出。
- SPEC §3.6 与 §5.8 的示例已同步改成这个顺序。

## D4 空持仓时也要给"类别首选符号"取价

- SPEC §5.2 说"对持仓里的每个符号解析价格"，但 §9-T49 要求空持仓时 `plan` 能下单。
- 实现取价集合 = 持仓符号 ∪ 有权重的类别的 `preferred_symbol`。
  没有这一步，第一次用的人（还没买入任何东西）会拿不到一手的价格。

## D5 `--offline` 只拦需要联网的行情源

- SPEC §5.2 的离线规则写成"用缓存，没有就报错"。
- 实现里 `provider=csv` 与 `provider=mock` 在 `--offline` 下照常工作——它们本来就是本地数据，
  拒绝它们只会让"完全离线演示"跑不起来。只有 `tencent` / `frankfurter` 会被拦。

## D6 `--refresh --offline` 的检查放在取价之前

- 两个参数互相矛盾，属于用法错误。实现里在 `prices` 一进命令就检查，
  报 `invalid_input`（退出码 2），不会先去联网再失败。

## D7 `mock` 提供方的时间戳就是 fixture 里的固定时间

- `fixtures/*.mock.json` 的 `fetchedAt` 是固定字符串（`2026-01-01T00:00:00+00:00`）。
- 因此演示数据在 `prices` 里会显示"缓存"（按 TTL 判定为过期）。这是故意的：
  示例数据本来就不是实时行情，标成"新"会误导。

## D8 `--verbose` 的日志文案

- SPEC §4.1 只说"stderr 增加请求次数、缓存命中、耗时"。
- 实现的具体格式是 `[info] 请求完成 HTTP 200，12ms：<脱敏 URL>`、
  `[info] 行情缓存命中 VTI（…）`、`[info] 行情：请求 1 次（重试 0 次），缓存命中 2 个`。

## D9 配置里的 `contribution.amount` 缺省时 `plan` 报 `cash_required`

- SPEC §4.2 说 `--cash` 不给就用 `contribution.amount`，但没说两者都没有时怎么办。
- 实现报退出码 2 `cash_required`，并提示两种补法。不做"默认 0"——那会让人以为没下单是 bug。
